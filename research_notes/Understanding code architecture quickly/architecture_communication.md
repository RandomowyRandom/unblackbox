# Communicating Software Architecture, Structure and Design Patterns to Humans

Evidence labels used throughout: [EMPIRICAL] = controlled experiment, field study, survey or systematic review with data; [PRACTITIONER] = practitioner consensus, standards, widely used frameworks, experience reports; [OPINION] = theory, argument or single-author advice without direct outcome data. Research window covers sources up to 2026; no 2024 to 2026 empirical study on C4 or architecture-diagram comprehension was found (see Gaps).

## 1. Architecture description approaches (C4, 4+1, arc42, ISO/IEC/IEEE 42010, Views and Beyond) and their shared principles

### Takeaway
All five approaches converge on the same few ideas: describe a system through several separate views, each answering one set of stakeholder concerns; refine structure hierarchically (zoom levels); and tie static structure to concrete runtime scenarios. None of them has been validated by a controlled comprehension experiment that I could find; their authority is practitioner consensus and standardization.

### Cited Findings
- [PRACTITIONER] C4 describes itself as "an easy to learn, developer friendly approach to software architecture diagramming," built from a set of hierarchical abstractions (software system, container, component, code) with matching hierarchical diagrams, plus supporting diagrams (system landscape, dynamic, deployment); it is "notation independent" and tooling independent. — [c4model.com](https://c4model.com/)
- [PRACTITIONER] C4 frames its diagrams as "maps of your code" at different levels of detail, explicitly compared to zooming in and out in Google Maps. Levels: System Context (starting point, how the system fits into the world around it), Container (applications and data stores inside the system), Component (components inside one container), Code (implementation of one component, e.g. a UML class diagram). Stated uses include communication, onboarding, architecture reviews, risk identification and threat modelling. — [C4 introduction](https://c4model.com/introduction)
- [PRACTITIONER] Simon Brown's core advice, as reported in a 2024 to 2025 GOTO podcast, is to start with only the top two levels (System Context and Container). — [GOTO podcast episode 449](https://gotopia.tech/episodes/449/c4-model) (via search summary; transcript not read directly)
- [PRACTITIONER] Kruchten's 4+1 View Model (IEEE Software 12(6), Nov 1995, pp. 42 to 50) describes a system through multiple concurrent views: Logical (object model of the design), Process (concurrency and synchronization), Development (the programmer's view, software management/module organization), Physical (mapping of software onto hardware, distribution). The "+1" is a small set of scenarios/use cases that tie the views together and are used to discover, illustrate and validate architectural elements. — [Kruchten 1995 PDF](https://www.ics.uci.edu/~michele/Teaching/INF117-S08/Krutchten%204+1View%20SWArch.pdf); [CISC322 slides](https://research.cs.queensu.ca/home/ahmed/home/teaching/CISC322/F08/slides/CISC322_06_4and1Views.pdf)
- [PRACTITIONER] arc42 is a 12-section template (Introduction and Goals, Constraints, Context and Scope, Solution Strategy, Building Block View, Runtime View, Deployment View, Crosscutting Concepts, Architectural Decisions, Quality Requirements, Risks and Technical Debt, Glossary). The Building Block View is "refined hierarchically" and is usually the largest section; the Runtime View documents important runtime scenarios; every section is tailorable; in use since 2005; a one-page "arc42 canvas" variant exists. — [arc42 overview](https://arc42.org/overview)
- [PRACTITIONER, standard] ISO/IEC/IEEE 42010 core model: stakeholders have concerns; viewpoints frame concerns; views (governed by viewpoints) address them. The 2022 second edition generalizes "system of interest" to "entity of interest," replaces "architecture model" with "architecture view component," lets one viewpoint govern one or more views, and defines "aspect" and "stakeholder perspective" more fully. An ICTU review found no major differences between the 2011 and 2022 editions. — [NORA wiki ISO 42010](https://noraonline.nl/wiki/ISO_42010); [TRAK ISO 42010 page](https://trak.sourceforge.io/iso_42010.html); [ISO 42010:2022 sample](https://cdn.standards.iteh.ai/samples/74393/fc7b7f103d8446a4b87a3261e31370d3/ISO-IEC-IEEE-42010-2022.pdf)
- [PRACTITIONER, contested reading] An OMG issue discussion argues that the 2022 edition's removal of multiplicities makes inclusion of viewpoints a "may" rather than a "shall." — [OMG UAF issue 14-152](https://issues.omg.org/issues/UAF14-152)
- [PRACTITIONER] SEI's "Documenting Software Architectures: Views and Beyond" (Clements et al., 1st ed. 2002, 2nd ed. 2010) organizes views into three viewtypes: Module (implementation units; relations is-a, is-part-of, depends-on; styles decomposition, uses, generalization, layers), Component-and-Connector (runtime elements and interaction pathways; styles pipe-and-filter, client-server, peer-to-peer, shared data, publish-subscribe, communicating processes), and Allocation (mapping software to environment; styles deployment, install, work assignment). — [Practical Method for Documenting Software Architectures (academia.edu)](https://www.academia.edu/118502096/A_Practical_Method_for_Documenting_Software_Architectures); [Pearson 2nd edition listing](https://www.pearson.com/subject-catalog/p/documenting-software-architectures-views-and-beyond/P200000000186/9780132488594)
- [OPINION/case illustration] A 2025 Zenodo "research guide" on C4 (Univ. of Piraeus / Univ. of Galway) claims C4 improves stakeholder communication and maintainability, but supports this only with a case illustration (FAME Data Marketplace), not measured outcomes. — [Zenodo record 15090175](https://zenodo.org/records/15090175)

### Inferences
- Shared principle 1, separation of concerns across views: 4+1 (five views), Views and Beyond (three viewtypes), ISO 42010 (viewpoint per set of concerns) and arc42 (building block, runtime, deployment views) all reject the "one big diagram" in favor of several focused ones.
- Shared principle 2, hierarchical zoom: C4's four levels and arc42's hierarchically refined building block view are the same idea; Views and Beyond's decomposition style is the module-viewtype version of it.
- Shared principle 3, scenarios as glue: Kruchten's "+1" scenarios, arc42's runtime view and C4's dynamic diagrams all bind abstract structure to a concrete walk-through. This aligns with Bret Victor's "step down" argument (section 3).
- Shared principle 4, audience-driven selection: ISO 42010 makes stakeholder concerns the selection criterion; C4 implicitly does so by recommending most audiences stop at levels 1 and 2.
- The C4 levels map roughly: C4 Context/Container ≈ arc42 Context and Scope + top-level Building Block View; C4 Container/Deployment ≈ 4+1 Physical / V&B Allocation; C4 Component ≈ 4+1 Logical/Development / V&B Module; C4 Dynamic ≈ 4+1 Scenarios / arc42 Runtime View / V&B C&C behavior.

### Gaps
- No controlled experiment or survey measuring comprehension benefits of C4, arc42, 4+1 or 42010-conformant documentation was found (searched for 2024 to 2025 C4 empirical studies explicitly). Their effectiveness claims are practitioner consensus.
- I did not retrieve c4model.com's FAQ page, so the exact official wording on whether the Code level is optional/not recommended is unverified; the "start with context and container" advice is sourced only via a podcast summary.
- Views and Beyond's "seven rules for sound documentation" were not retrieved.

## 2. Empirical evidence on diagram comprehension (layout, UML vs text, sequence vs collaboration, Physics of Notations, visual variables, color)

### Takeaway
The most robust layout finding is that edge crossings hurt graph comprehension more than other aesthetics, and that layout quality matters more as diagrams grow and matters more for novices than experts. Notation-design theory (Moody's Physics of Notations) is widely cited but mostly applied uncritically; its principles are design heuristics, not individually validated laws. Comparative results between diagram types (sequence vs collaboration) are small and domain-dependent.

### Cited Findings
- [EMPIRICAL] Purchase's user study of five graph aesthetics found minimizing edge crossings was "overwhelmingly" the most beneficial for understanding graph structure, and the most important of the five. — [Purchase GD 1997, Springer](https://link.springer.com/content/pdf/10.1007/3-540-63938-1_67.pdf); summarized in [Huang et al. eye-tracking study, arXiv 0810.4431](https://arxiv.org/pdf/0810.4431)
- [EMPIRICAL, preference not performance] Purchase, Allder and Carrington (JGAA 2002) collected subject preferences to build an ordered list of preferred aesthetic features in UML class and collaboration diagrams; this is a preference study, not a comprehension-performance study. — [JGAA paper](https://jgaa.info/index.php/jgaa/article/download/paper54/2911)
- [EMPIRICAL, nuance] For path-tracing tasks, what matters is the number of crossings on the path being traced, not total crossings (Ware et al., as reported); later work argues a drawing better on the crossing metric is not necessarily better for comprehension. — [Huang et al. arXiv 0810.4431](https://arxiv.org/pdf/0810.4431); [Structure Based Aesthetics, arXiv 1609.07688](https://arxiv.org/pdf/1609.07688)
- [EMPIRICAL] Störrle (2011) notes that earlier evidence for layout effects on UML understanding was "weak and inconclusive," then found with very high significance a notable impact of layout quality on cognitive load. — [DTU Orbit, "On the impact of layout quality to understanding UML diagrams"](https://orbit.dtu.dk/en/publications/on-the-impact-of-layout-quality-to-understanding-uml-diagrams/); [PDF](https://backend.orbit.dtu.dk/ws/files/6282242/PID1910517.pdf)
- [EMPIRICAL] Follow-ups: the layout benefit did not differ by UML diagram type, and experts benefited less from good layout than novices (2012); small diagrams are usable regardless of layout, but as size grows layout quality increasingly drives performance (MODELS 2014 "Size matters"); the 2016 SoSyM journal version analysed topographic layout flaws in 60 diagrams across five UML types, confirmed earlier results and refined the recommendations. — [DTU Orbit, "Diagram size vs layout flaws"](https://orbit.dtu.dk/en/publications/diagram-size-vs-layout-flaws-understanding-quality-factors-of-uml/); [Störrle talk "Good, Bad, Ugly: Layout Matters"](https://www.pst.ifi.lmu.de/~stoerrle/talks/Good_Bad_Ugly-LayoutMatters.pdf); [VL 4d Size](https://backend.orbit.dtu.dk/ws/files/120654649/VL_4d_Size.pdf)
- [EMPIRICAL, weak] Eye-tracking: a 4-participant pilot (explicitly preliminary) and a poster study with n=29 report that layout quality, experience and diagram type change how modelers read diagrams, with novices and experts using different strategies on poorly laid-out diagrams. — [DTU VL 4e Behavior poster](https://backend.orbit.dtu.dk/ws/files/100928142/VL_4e_Behavior_Poster.pdf); [Strathclyde eye-tracking pilot](https://strathprints.strath.ac.uk/79510)
- [EMPIRICAL] Glezer, Last, Nachmany and Shoval (IST 2005, student subjects): collaboration diagrams were easier to comprehend than sequence diagrams for real-time systems, with no difference for management information systems; MIS diagrams were easier to comprehend than RT diagrams regardless of type. — [BGU CRIS record](https://cris.bgu.ac.il/en/publications/quality-and-comprehension-of-uml-interaction-diagrams-an-experime-2/); cited as such in [Felderer and Herrmann 2019, SQJ](https://link.springer.com/content/pdf/10.1007/s11219-018-9407-9.pdf)
- [OPINION/theory] Moody's "Physics of Notations" (IEEE TSE 2009) defines cognitive effectiveness as the speed, ease and accuracy with which a representation can be processed, and argues it must be designed in. It has a descriptive part (how notations communicate) and a prescriptive part of nine principles. The RE09 variant lists: perceptual immediacy, visual expressiveness, graphic economy, dual coding, semiotic clarity, manageable complexity, perceptual discriminability, cognitive fit, cognitive integration. Semiotic clarity demands a one-to-one correspondence between symbols and concepts. — [PoN RE09 paper](https://homepages.uc.edu/~niunn/courses/RE-refs%5CPoN-RE09.pdf); [Waterloo CS846 review notes](https://cs.uwaterloo.ca/%7Ejmatlee/Teaching/CS846/Schedule/Jan30/Kevin.pdf); [KIT publication](https://publikationen.bibliothek.kit.edu/1000079942/6400321)
- [EMPIRICAL, meta-level critique] Van der Linden and Hadar (IEEE TSE 45(8), 2019) reviewed 70 peer-reviewed applications of PoN: when used to design new notations, most applications adopted PoN "with little critical thought," rarely considered fit to context, and gave few verifiable details or data; they call for careful application and more designer guidance. — [Northumbria research portal](https://researchportal.northumbria.ac.uk/en/publications/a-systematic-literature-review-of-applications-of-the-physics-of-/); [Bristol record](https://research-information.bris.ac.uk/en/publications/a-systematic-literature-review-of-applications-of-the-physics-of-/); [ENASE 2016 preliminary paper](https://www.scitepress.org/Papers/2016/58958/)
- [OPINION] A student thesis notes PoN does not address how to lay out or represent individual diagrams well (it targets notation design, not diagram instance quality). — [UNamur thesis "Towards the Operationalization of the Physics of Notations"](https://researchportal.unamur.be/en/studentTheses/towards-the-operationalization-of-the-physics-of-notations)
- [PRACTITIONER] Color: C4 says no color scheme is required, but color must be used consistently within and across diagrams, and authors should consider black-and-white printing and color blindness. — [C4 notation](https://c4model.com/diagrams/notation)

### Inferences
- Layout effects are real but conditional: they bite on larger diagrams and for novices, which is exactly the audience of an onboarding explainer. Small, well-laid-out diagrams are the safe default.
- Crossing minimization is the one aesthetic with consistent support; crossings on the path the viewer is currently tracing matter most, which argues for highlighting the active path.
- Diagram-type choice (sequence vs collaboration) matters less than domain and task; no type is universally superior.
- PoN is best treated as a checklist of heuristics (e.g. semiotic clarity, perceptual discriminability, manageable complexity) rather than an empirically validated theory.

### Gaps
- UML vs textual descriptions: I did not retrieve a primary study directly comparing UML diagrams with text for comprehension; no claim made.
- Bertin's visual variables (position, size, shape, value/brightness, color hue, orientation, texture) and their use in PoN's "visual expressiveness" principle: known from background knowledge, not verified in this session.
- Gestalt principles (proximity, similarity, enclosure, connectedness) applied to software diagrams: not researched; no software-specific experiment retrieved.
- Color-specific comprehension experiments for software diagrams: none retrieved.
- Moody and van Hillegersberg's PoN-based critique of UML visual syntax: not retrieved.

## 3. Diagram-as-explanation: progressive disclosure, zoom, incremental reveal, Tufte, Bret Victor

### Takeaway
Learning-science evidence supports segmenting content into learner-paced chunks, signaling the organization of the material, cutting extraneous material, and pairing words with pictures. Evidence does not support animation per se: when content is held equal, animated graphics rarely beat well-designed static ones for conveying complex systems, and small multiples beat animation for analysis. Strict data-ink minimalism is less supported than its popularity suggests.

### Cited Findings
- [EMPIRICAL] Mayer's Cambridge Handbook chapter (2014) reports median effect sizes for the coherence principle (exclude extraneous material; positive in 23 of 23 tests, d ≈ 0.86) and the signaling principle (cues that highlight the organization of essential material; 24 of 28 tests, d ≈ 0.41). — [Cambridge Handbook chapter](https://resolve-he.cambridge.org/core/books/cambridge-handbook-of-multimedia-learning/principles-for-reducing-extraneous-processing-in-multimedia-learning-coherence-signaling-redundancy-spatial-contiguity-and-temporal-contiguity-principles/CD5B7AE1279A9AB81F8EEBB53DBEC86E)
- [EMPIRICAL] Mayer's 2017 review (J. Computer Assisted Learning) as summarized: coherence d ≈ 0.70, signaling d ≈ 0.46, segmenting (learner-paced segments rather than a continuous unit) d ≈ 0.70, multimedia principle (words plus pictures vs words alone) median d = 1.67; segmenting, pre-training and modality are grouped as principles for managing essential processing; some principles are stronger for low-knowledge than high-knowledge learners. Effect sizes differ from the 2014 chapter; the discrepancy is not explained in the sources retrieved. — [Mayer 2017, JCAL 10.1111/jcal.12197](https://zendy.io/title/10.1111/jcal.12197); [Dartmouth summary of 12 principles](https://services.dartmouth.edu/TDClient/1806/Portal/KB/PrintArticle?ID=171655)
- [EMPIRICAL review] Tversky, Morrison and Betrancourt (IJHCS 57, 2002) found no reliable advantage of animation over static graphics for conveying complex systems; apparent advantages usually came from animations carrying more information or interactivity than the static comparison. Proposed causes: animations often violate the Apprehension Principle (graphics must be accurately perceived and appropriately conceived); the Congruence Principle says the graphic's structure should match the content's. They suggest animation may help in other cases, e.g. real-time reorientation in time and space. — [Tversky et al. 2002 PDF (Stanford)](https://hci.stanford.edu/courses/cs448b/papers/Tversky_AnimationFacilitate_IJHCS02.pdf)
- [EMPIRICAL] Robertson, Fernandez, Fisher, Lee and Stasko (IEEE TVCG/InfoVis 2008): for trend analysis, animation was the least effective form; both static alternatives (overlaid traces and small multiples) were significantly faster, and small multiples were more accurate. Received the InfoVis Test of Time award in 2018 (per co-author's blog). — [Robertson et al. 2008 PDF](https://faculty.cc.gatech.edu/~stasko/papers/infovis08-anim.pdf); [Fisher retrospective](https://medium.com/@FisherDanyel/effectiveness-of-animation-in-trend-visualization-ten-years-later-e2f52b433526)
- [OPINION, influential] Tufte coined "chartjunk" (non-informative or information-obscuring elements) and the data-ink ratio (data ink / total ink; maximize it, erase non-data ink "within reason"); he recommends small multiples (repeated small graphics) for comparison and data density. — [Wikipedia, Edward Tufte](https://www.wikipedia.org/wiki/Edward_Tufte); [Danny Yee review of VDQI](https://dannyreviews.com/h/Visual_Display.html)
- [EMPIRICAL, counterpoint] Bateman et al. (CHI 2010) compared minimalist and embellished (Nigel Holmes style) charts: no difference in interpretation accuracy or response time, and embellished charts were recalled better after more than 12 days; authors caution against embellishment as a general strategy. Stephen Few (2011) argued the benefit holds only where embellishment conveys the message. — [Bateman et al. PDF](https://vis.csail.mit.edu/classes/6.859/readings/pdfs/Bateman-UsefulJunk.pdf); [Few 2011 critique](https://webspace.science.uu.nl/~telea001/uploads/VACourse/Few11.pdf); [eagereyes discussion](https://eagereyes.org/blog/2010/chart-junk-considered-useful-after-all)
- [OPINION, influential] Bret Victor, "Up and Down the Ladder of Abstraction" (Oct 2011): insight comes from moving between concrete instances and abstract views; stepping up abstracts over a variable (time, parameters, data), e.g. plotting a whole trajectory instead of watching a car move; stepping down (selecting a point in the abstraction to see the concrete case) is "as important as stepping up"; interactive control over time and parameters makes the ladder usable. — [worrydream.com/LadderOfAbstraction](http://worrydream.com/LadderOfAbstraction/)

### Inferences
- "Build the diagram step by step" is supported indirectly by segmenting and signaling evidence, not by software-specific experiments. The mechanism is controlling what is on screen at once, not the motion itself.
- Animation's best-supported role is transition and reorientation (zooming from one level to the next, following one message along a path), consistent with Tversky's exception; animation used to "show behavior" should be checked against a small-multiples or static-sequence alternative.
- Victor's ladder suggests pairing each abstract diagram with a concrete instance (one request, one trace) and going back up.
- Minimalism is defensible for accuracy (coherence d ≈ 0.7 to 0.86), but light, meaningful embellishment may aid long-term recall (Bateman); the two are not contradictory if decoration is tied to meaning.

### Gaps
- No controlled study found that compares incremental build-up vs show-all-at-once for software architecture diagrams specifically.
- Bret Victor's "Explorable Explanations" (2011) essay was not retrieved; no claims made from it.
- The Robertson et al. presentation-condition results (vs the analysis condition) were not verified.
- Segmenting effect size comes only from a secondary summary of Mayer 2017.

## 4. Software visualization research (code cities, dependency graphs, trace visualization): evidence vs impressiveness

### Takeaway
A few tools have positive controlled experiments (CodeCity; EXTRAVIS trace visualization), usually run by the tool authors against weak IDE baselines. The field overall evaluates poorly: about 62% of proposed software visualization approaches in SOFTVIS/VISSOFT had no evaluation. Impressive visuals are common; demonstrated comprehension gains are rare.

### Cited Findings
- [EMPIRICAL] Merino, Ghafari, Anslow and Nierstrasz (JSS 2018) reviewed all 387 SOFTVIS/VISSOFT papers and analysed 181 with extractable evaluation details: 62% of proposed software visualization approaches include no evaluation; they argue evaluations should measure recollection, usability and engagement as well as time and correctness, and involve real target users in realistic settings. — [SCG Bern project page](https://scg.unibe.ch/research/softvis-eval); [Merino publication page](https://leonelmerino.github.io/publication/2018-10-01-A-Systematic-Literature-Review-of-Software-Visualization-Evaluation)
- [EMPIRICAL review] Chotisarn, Merino et al. (J. Visualization 2020) analysed 1,440 entries and selected 105 full papers from 2013 to 2019 on modern software visualization (characteristics, not evaluation quality). — [arXiv 2003.00643](https://arxiv.org/pdf/2003.00643)
- [EMPIRICAL] Wettel, Lanza and Robbes (ICSE 2011) ran a controlled experiment with 41 participants from academia and industry across four locations in three countries, comparing CodeCity (3D city metaphor) with a baseline of Eclipse plus Excel: statistically significant increase in task correctness and decrease in completion time. — [USI tech report Wett2010a](https://www.inf.usi.ch/faculty/lanza/PUBS/M/Wett2010a.pdf); [CORE PDF](https://core.ac.uk/download/20651814.pdf); [slides](https://de.slideshare.net/wettel/software-systems-as-cities-a-controlled-experiment)
- [EMPIRICAL] Cornelissen, Zaidman and van Deursen (IEEE TSE 37(3), 2011): eight comprehension tasks on a representative system; Eclipse-only control vs Eclipse plus EXTRAVIS trace visualization; 22% less time and 43% more correct answers for the trace-visualization group, both statistically significant. — [TSE preprint PDF](https://azaidman.github.io/publications/cornelissenTSE2010.pdf); [TU Delft repository](https://repository.tudelft.nl/record/uuid:6d3ac25b-ac24-47e9-adff-595e5da3c5b6)
- [EMPIRICAL] Fittkau, Finke, Hasselbring and Waller (ICPC 2015) replicated the EXTRAVIS design comparing EXTRAVIS with their ExplorViz tool on a differently sized system. — [ICPC 2015 preprint](https://oceanrep.geomar.de/id/eprint/28324/1/Comparing_Trace_Visualizations_ICPC2015_preprint.pdf)

### Inferences
- Both positive experiments compared a visualization tool against raw IDE or spreadsheet baselines, so they show "a structured overview beats none," not "3D cities beat a good 2D diagram."
- Trace visualization (showing actual runtime behavior) has the strongest numeric effect retrieved, which supports Victor's and Kruchten's emphasis on concrete scenarios.
- Code cities are a case of "popular and visually impressive, thinly evidenced": one positive author-run experiment, no independent replication retrieved.

### Gaps
- Exact CodeCity effect sizes (commonly quoted as about +24% correctness and -12% time) were not verified in this session.
- Fittkau et al. replication outcomes were not retrieved.
- No independent replication of CodeCity found; no controlled studies of dependency-graph views (e.g. DSMs, module graphs) retrieved.
- VR/AR code-city studies from 2020 to 2026 not researched.

## 5. Explaining design patterns: presentation structure, problem-first vs solution-first, teaching evidence

### Takeaway
Evidence that patterns help novices learn design is weak; evidence that explicitly documenting which pattern code uses speeds correct maintenance is moderate (two controlled experiments). Problem-first, hands-on presentation is the dominant recommendation in CS education reports, but it rests on experience reports rather than controlled comparisons.

### Cited Findings
- [EMPIRICAL review] Zhang and Budgen (IEEE TSE 38(5), 2012, pp. 1213 to 1231), mapping study of literature to end of 2009 on the 23 GoF patterns (20 primary studies per Zhang's thesis): mixed evidence on usefulness; patterns do not appear to help novices learn about design; some qualitative support for helping maintenance; recommends case studies of key patterns' maintenance impact. — [Durham repository](https://durham-repository.worktribe.com/output/1476205/what-do-we-know-about-the-effectiveness-of-software-design-patterns); [Zhang PhD thesis](https://etheses.durham.ac.uk/id/eprint/859/)
- [OPINION/review] Budgen's follow-up "Design Patterns: Magic or Myth?" (IEEE Software 30(2), 2013). — [Durham repository listing](https://durham-repository.worktribe.com/output/1476205)
- [EMPIRICAL] Prechelt, Unger-Lamprecht, Philippsen and Tichy (IEEE TSE 28(6), 2002, pp. 595 to 606): two controlled experiments (74 German graduate students, Java; 22 US undergraduates, C++). Pattern-relevant maintenance tasks were completed faster or with fewer errors when explicit (redundant) pattern documentation was present in code comments. — [FAU CRIS record](https://cris.fau.de/publications/115927284); [KIT publication](https://publikationen.bibliothek.kit.edu/22697/1966)
- [PRACTITIONER/experience report] Ó Cinnéide and Tynan (2004) argue the lecture-based approach is "particularly poorly suited" to teaching patterns and propose a problem-based approach where students apply patterns to exercises and experience their benefits. — [A Problem-based Approach to Teaching Design Patterns](https://eprints.teachingandlearning.ie/id/eprint/3312/)
- [EMPIRICAL, postgraduate] Chatzigeorgiou et al. (Computers and Education, 2008): postgraduates built one system version without and one with patterns, allowing measurement of pattern preference and ability to match design problems to patterns. — [Record](https://ersearch2.cvtisr.sk/vufind/SummonRecord/FETCH-LOGICAL-c361t-af08a860420f37f4d1d4a2a3e161a0ac1f5383613c127dbc03aef9e7ef1f14de3?lng=en)
- [PRACTITIONER/experience report] Modified PBL for patterns in limited hours (Huang and Yang 2008) and PBL for GRASP patterns (dos Santos, WEI, Portuguese) are experience reports, not controlled studies. — [Infona record](https://www.infona.pl/resource/bwmeta1.element.ieee-art-000004709353); [SBC WEI paper](https://sol.sbc.org.br/index.php/wei/article/download/40291/40063)

### Inferences
- The "build it without the pattern first, feel the pain, then refactor to the pattern" sequence (Chatzigeorgiou-style, Ó Cinnéide-style) is the best available teaching shape, but its advantage over solution-first is not experimentally isolated.
- Naming the pattern explicitly where it appears in code is the one presentation move with controlled-experiment support (Prechelt), and only for people who already know the pattern.
- Because patterns do not reliably help novices learn design (Zhang and Budgen), an explainer aimed at newcomers should lead with the problem and the forces, not the pattern name or UML structure diagram.

### Gaps
- The GoF book's pattern template (Intent, Also Known As, Motivation, Applicability, Structure, Participants, Collaborations, Consequences, Implementation, Sample Code, Known Uses, Related Patterns) and Alexander's problem/context/forces/solution form are known from background knowledge but were not retrieved and verified in this session.
- No SIGCSE or ITiCSE controlled study comparing problem-first vs solution-first pattern teaching was found in the searches run.
- No study on before/after refactoring demonstrations as an explanation format was retrieved.

## 6. Practitioner sources on explaining a system to newcomers (walkthroughs, code tours, ADRs, README onboarding, Diátaxis)

### Takeaway
Field studies show developers explain systems mostly with informal sketches, rarely UML, and that design rationale is often lost; newcomers orient by early experimentation and by internalizing structure and culture. Practitioner tools (CodeTour, ADRs, Diátaxis "explanation" docs) target exactly these gaps: anchored walkthroughs, preserved rationale, and a distinct "why" genre separate from tutorials, how-tos and reference.

### Cited Findings
- [EMPIRICAL] Petre (ICSE 2013) interviewed 50 professional engineers at 50 companies: 35 used no UML, 11 used it selectively, 3 for code generation, 1 retrofitted models, none wholeheartedly; UML use tended to be in early design or implementation, rarely both (counts via Greg Wilson's review). — [ICSE 2013 page](https://2013.icse-conferences.org/content/uml-practice.html); [paper PDF](https://www.ics.uci.edu/~andre/informatics223s2017/petre.pdf); [Never Work in Theory review](https://neverworkintheory.org/2013/06/13/uml-in-practice-2.html); follow-up [Petre 2014 SoSyM](https://oro.open.ac.uk/41542)
- [EMPIRICAL] Cherubini, Venolia, DeLine and Ko (CHI 2007), study of how developers "draw their code": most diagrams were transient because of the cost of turning whiteboard sketches into electronic form; drawings that documented design decisions were often lost. — [Microsoft Research page](https://www.microsoft.com/en-us/research/?p=154511); [Never Work in Theory summary](https://neverworkintheory.org/2011/06/30/lets-go-to-the-whiteboard.html)
- [EMPIRICAL] Baltes and Diehl (FSE 2014 / arXiv 2017): 394-respondent survey; whiteboard most common sketch medium (40%), then computer (39%) and paper (18%); most digital sketches and over a third of analog sketches are archived; 47 sketches from 13 developers analysed in depth; only 9% of sketches were "pure" UML (per author's comment, secondary). — [arXiv 1706.09172](https://arxiv.org/pdf/1706.09172); [dev.to author comment](https://dev.to/s_baltes/comment/1ci9)
- [EMPIRICAL] Dagenais, Ossher, Bellamy, Robillard and de Vries (ICSE 2010), grounded theory with 18 newcomers in 18 IBM projects: integration is shaped by early experimentation, internalizing structures and cultures, and progress validation; newcomers are framed as explorers orienting in an unfamiliar "landscape," with identifiable orientation aids and obstacles. — [McGill PDF](https://www.cs.mcgill.ca/~martin/papers/icse2010.pdf)
- [PRACTITIONER] Microsoft CodeTour (VS Code extension) records and replays guided walkthroughs: a tour is "a series of interactive steps," each tied to a directory, file or line with a markdown description; tours are JSON in a `.tours` folder checked into the repo; described as "like a table of contents" for onboarding; uses include onboarding and re-onboarding, bug reports, PR/code review context and interactive tutorials. — [github.com/microsoft/codetour](https://github.com/microsoft/codetour)
- [PRACTITIONER] Nygard's ADRs (2011): without recorded rationale, newcomers can only "blindly accept" a past decision or blindly change it, both risky. Format: Title, Context (forces at play), Decision ("We will..."), Status, Consequences (positive, negative, neutral); one to two pages; stored in the repo (e.g. doc/arch/adr-NNN.md), numbered, never reused, superseded records kept. — [Cognitect blog](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)
- [PRACTITIONER] arc42 dedicates a section to Architectural Decisions and one to Solution Strategy (core ideas). — [arc42 overview](https://arc42.org/overview)
- [PRACTITIONER] Diátaxis defines Explanation as "understanding-oriented," discursive documentation answering "Can you tell me about...?", read away from the keyboard; unlike tutorials (learning goal), how-tos (task) and reference (the machinery), explanation has no natural boundary, so the writer bounds it, often with a "why" question. Advice: make connections, provide context (design decisions, history, constraints), talk "about" the subject, admit opinion and weigh alternatives, keep instruction and reference out. Analogy: McGee's "On Food and Cooking" vs a recipe book. — [diataxis.fr/explanation](https://diataxis.fr/explanation/)

### Inferences
- What newcomers lack most is rationale and orientation, not notation: field studies show decisions get lost (Cherubini) and newcomers orient by exploring (Dagenais). ADRs and Diátaxis explanation target the "why"; CodeTour targets anchored orientation.
- The practical lingua franca is the informal boxes-and-arrows sketch, not UML (Petre; Baltes and Diehl). An explainer should use that vocabulary, but disciplined by C4-style rules (section 7).
- A code tour is a linear, narrated, anchored sequence of locations; it is structurally close to a video script.

### Gaps
- README-driven development / README onboarding: no source retrieved; no claims made.
- No controlled study found on whether CodeTour-style tours or ADRs measurably speed onboarding.
- Steinmacher et al.'s work on newcomer barriers in open source was surfaced in search but not read.

## 7. Common failure modes (boxes-and-lines ambiguity, mixed abstraction levels, too many elements, unlabeled arrows, missing legend, no narrative)

### Takeaway
The failure modes are well catalogued by practitioners and partly backed by experiments: ambiguity of symbols (semiotic clarity), mixed abstraction levels, unlabeled or bidirectional arrows, missing title/legend, and oversize diagrams. Size and crossings have empirical backing; the labeling/legend rules are practitioner consensus.

### Cited Findings
- [PRACTITIONER] C4 introduction: asking a developer to diagram architecture often yields "a confused mess of boxes and lines"; typical issues are ambiguous element meaning, unlabelled relationships, generic terms like "business logic," and mixed levels of abstraction. — [C4 introduction](https://c4model.com/introduction)
- [PRACTITIONER] C4 notation checklist: every diagram needs a title stating type and scope, and a key/legend; acronyms must be understood by all audiences or explained in the legend; every element states its type and a short responsibility description; every container/component states its technology; every line is one-directional and labeled consistently with its direction and intent, avoiding vague one-word labels; inter-container relationships name technology/protocol; ask whether each diagram can be mostly understood without a narrative. — [C4 notation](https://c4model.com/diagrams/notation)
- [OPINION/theory] Semiotic clarity (one symbol per concept, one concept per symbol) and manageable complexity are PoN principles directly addressing ambiguity and overload. — [PoN RE09](https://homepages.uc.edu/~niunn/courses/RE-refs%5CPoN-RE09.pdf); [Waterloo CS846 notes](https://cs.uwaterloo.ca/%7Ejmatlee/Teaching/CS846/Schedule/Jan30/Kevin.pdf)
- [EMPIRICAL] Too many elements: as diagram size increases, layout quality increasingly drives performance; small diagrams are usable regardless of layout. — [Störrle, DTU Orbit](https://orbit.dtu.dk/en/publications/diagram-size-vs-layout-flaws-understanding-quality-factors-of-uml/)
- [EMPIRICAL] Edge crossings are the most damaging aesthetic of those tested. — [Purchase 1997](https://link.springer.com/content/pdf/10.1007/3-540-63938-1_67.pdf)
- [EMPIRICAL] Extraneous material lowers learning (coherence principle, d ≈ 0.86 in 23 of 23 tests). — [Cambridge Handbook chapter](https://resolve-he.cambridge.org/core/books/cambridge-handbook-of-multimedia-learning/principles-for-reducing-extraneous-processing-in-multimedia-learning-coherence-signaling-redundancy-spatial-contiguity-and-temporal-contiguity-principles/CD5B7AE1279A9AB81F8EEBB53DBEC86E)
- [EMPIRICAL] Diagrams without words: the multimedia principle (words plus pictures beat words alone) has a median d of 1.67 per Mayer 2017 as summarized. — [Mayer 2017 JCAL](https://zendy.io/title/10.1111/jcal.12197)
- [EMPIRICAL] Missing rationale: design-decision drawings are often transient and lost. — [Cherubini et al. 2007](https://www.microsoft.com/en-us/research/?p=154511)

### Inferences
- C4's "understandable without narrative" test and Mayer's multimedia principle are complementary: the diagram should be self-describing (title, legend, labels) and also be accompanied by narration that carries the why.
- Mixed abstraction levels is the failure that zoom-level frameworks (C4, arc42 hierarchy) exist to prevent; one diagram = one level = one scope.
- Unlabeled arrows violate semiotic clarity because a bare line can mean calls, depends-on, data flow, or deploys-to.

### Gaps
- No controlled experiment found that isolates the effect of arrow labels or legends on comprehension.
- No numeric threshold for "too many elements" per architecture diagram was found in retrieved sources (commonly cited figures like "7 plus or minus 2" or "about 20 elements" were not verified).

## 8. Implications for an animated code-explainer video

### Takeaway
Sequence the video top-down through zoom levels (context, then containers, then only the one component that matters), build each frame incrementally with signaling, hold static frames for reading, use motion mainly for transitions and for following one concrete scenario, and narrate the why. Leave out everything that is not on the current story's path.

### Cited Findings
- [PRACTITIONER] Start with System Context and Container levels; most audiences need nothing deeper. — [GOTO podcast with Simon Brown](https://gotopia.tech/episodes/449/c4-model); [C4 introduction](https://c4model.com/introduction)
- [EMPIRICAL] Segment into learner-paced chunks, signal organization, remove extraneous material, pair words with pictures; pre-training is grouped with segmenting as managing essential processing. — [Mayer 2017](https://zendy.io/title/10.1111/jcal.12197); [Cambridge Handbook chapter](https://resolve-he.cambridge.org/core/books/cambridge-handbook-of-multimedia-learning/principles-for-reducing-extraneous-processing-in-multimedia-learning-coherence-signaling-redundancy-spatial-contiguity-and-temporal-contiguity-principles/CD5B7AE1279A9AB81F8EEBB53DBEC86E)
- [EMPIRICAL] Animation offers no general advantage over equivalent static graphics for complex systems; may help reorientation in time and space; small multiples beat animation for analysis. — [Tversky et al. 2002](https://hci.stanford.edu/courses/cs448b/papers/Tversky_AnimationFacilitate_IJHCS02.pdf); [Robertson et al. 2008](https://faculty.cc.gatech.edu/~stasko/papers/infovis08-anim.pdf)
- [EMPIRICAL] Concrete runtime traces improved comprehension time and correctness (22% and 43%). — [Cornelissen et al. 2011](https://azaidman.github.io/publications/cornelissenTSE2010.pdf)
- [EMPIRICAL] Explicitly naming patterns in code helps pattern-relevant maintenance. — [Prechelt et al. 2002](https://cris.fau.de/publications/115927284)

### Inferences
- Zoom sequence: (1) System Context: one box for the system, its users, external systems, labeled verb arrows; (2) Container: zoom into the box with an animated camera move so the parent boundary stays visible as a frame (reorientation is animation's supported use); (3) zoom into only the one container the story needs, show its 3 to 7 key components; (4) drop to code only for the one function or class that carries the idea, then zoom back out. This is Victor's ladder plus C4's levels.
- Step down to one concrete scenario after each structural level: send one request/message along the arrows, highlighting the active path (crossings on the traced path matter most), equivalent to Kruchten's "+1," arc42's runtime view, C4 dynamic diagrams and trace visualization.
- Incremental reveal: add elements in the order the narration names them (signaling); hold the completed frame long enough to read; avoid continuous motion while the viewer must read labels.
- Pre-train vocabulary: name the 3 to 5 key parts before showing the full diagram.
- Each frame: one level, one scope; a title naming level and scope; consistent shape/color mapping across all zoom levels with a brief legend on first use; colorblind-safe palette; every arrow one-way and labeled with a verb (and protocol at container level); keep element count small and layout stable between frames to avoid re-learning positions; minimize crossings.
- Patterns: show the problem first (the code or structure without the pattern and the pain it causes), then the refactored structure, then name the pattern explicitly. Do not open with a UML structure diagram of the pattern.
- Narration carries rationale: why this split, which alternatives were rejected, what constraints applied (Diátaxis explanation, ADR "context" and "consequences").
- Leave out: full class diagrams, every container/component, deployment detail unless it is the point, 3D code-city visuals (thin evidence), decorative motion, unlabeled lines, technology badges not referenced in narration. Light thematic illustration is acceptable if tied to meaning (Bateman), but it should not compete with the diagram.
- Expertise reversal: the scaffolding above matters most for novices; for an expert audience, fewer build-up steps and denser frames are acceptable (Störrle 2012: experts benefit less from good layout; Mayer: some principles weaker for high-knowledge learners).

### Gaps
- No study found that directly tests animated architecture explainers or zoom-transition videos for software comprehension; recommendations above are extrapolated from general multimedia learning, graph-layout and trace-visualization evidence.
